# SDLC

How a change gets from an idea to `develop` in this project. Generated by
`xez-onboard-opinionated` from the confirmed gate answers, so this file, `.xezar/checks/repo-gates.sh`
and `.xezar/pipeline/config.json` agree from day one.

The gate is one command:

```bash
.xezar/checks/repo-gates.sh
```

It runs `npm ci`, the security scan, `npm run typecheck`, `npm run lint`, `npm run format:check`,
`npm test`, `npm run build`, `npm run check:headers`, then the kit's repository checks. Exit 0 only
when every gate ran **and** passed. A gate that could not run is a failure, never a pass.

## The QA gate

QA is where a change is driven the way a user would drive it, rather than judged by reading it.
8cli is a command-line tool, so QA here means running the built CLI — `node dist/bin/8cli.js` —
against a real n8n and checking the JSON on stdout, the structured error on stderr and the exit
code.

The gate is awake in this project. A change that alters what a command prints, what it accepts or
what it exits with carries `needs-qa` and may not merge on `qa-failed`. A change that touches no
command surface carries `skip-qa`, and the reason is written in the pull request.

## The design gate

The design gate is **on**. A CLI's command names, flags, help text, output shape and exit codes are
the surface its users touch, and they are designed or they are accidents.

Every part of the design half is installed whether the gate is on or off: the four design labels,
`docs/designs/`, the design role skills and the design review workflow. What the gate decides is
only whether a change is _stopped_ for a design verdict. To turn it off, remove `needs-design` from
the labels a change must carry and say so here — one line, so nobody reads a sleeping rule as an
active one.

One honest limit: no browser tool is installed on the machine this project was onboarded from, so a
design review that needs to look at a rendered screen reports "not verifiable here" rather than
passing.

## Review loop

1. The author finishes and runs the gate.
2. A lane from the **review** chain that is not the authoring lane gives a verdict.
3. `changes-requested` hands the change back to the author, who answers every finding.
4. The reviewer re-checks only what changed, unless the change was large enough to invalidate the
   earlier read.

A cloud-lane write needs another vendor's review before it can merge. Rotating to another login of
the same vendor does not satisfy this.

## Self-review inside the author phase, and the repair counters

Before handing anything to a reviewer, the author reads its own diff as if somebody else wrote it
and fixes what it finds. That pass is part of authoring, not a review verdict — a model never
counts as the reviewer of its own work.

Two counters bound the loop. **Repair attempts**: three failed attempts at the same gate failure
stop the task and hand it back with what was tried. **Review rounds**: three rounds of
`changes-requested` on one change stop it and raise the question with the owner. A counter that
keeps climbing is a task that needs a decision, not another attempt.

## The QA and design self-verification exceptions

A QA or design verdict may be given by the authoring lane in exactly one case: the evidence is
mechanical and reproducible by anybody — a recorded command with its output, a captured screen —
and it is attached. The label is then `qa-self-verified`, never `qa-approved`. Anything that rests
on judgement goes to another lane.

## Security review

A diff that touches a trust boundary is routed to the security-review row by machine, not by
memory. The trust boundaries in this project are `.xezar/pipeline/config.json`, `.xezar/config.json`,
`.github/workflows/`, the `SessionStart` hook in `.claude/settings.json` and its loader
`.xezar/checks/leader-context.sh`, plus anything touching credential handling in
`src/keychain/` and `src/client/`.

A security review that found nothing is not a code review that passed. Both run.

## Architecture review

A change that decides how the system is cut, what owns what, or a quality the whole must hold gets
an architecture review and a decision record under `docs/architecture/`. It binds work beyond the
feature that raised it, so it is written down before the code lands.

## Acceptance

Acceptance asks one question: does the change do what the issue asked for? It is given against the
issue's own wording, by a lane that did not author the change, with the evidence named. Gates
passing is not acceptance.

## Deploy authority

This project has **no deploy and no rollback workflow**, so `deploy.environments` and
`deploy.rollback` are `[]` in `.xezar/pipeline/config.json` and both workflows refuse with that
reason. That is the recorded answer "this project has none", not an oversight.

Publishing is the one outward step: `.github/workflows/publish.yml` sends `@qodeca/8cli` to npm via
OIDC trusted publishing when a GitHub Release is published. **The owner authorises every release.**
The leader holds no publishing credential and never publishes.

## Two more conditional parts

- **Performance budgets**: `performance.budgets` is `[]`. A budget is a promise about the product,
  and nothing here invents one. The performance workflow is installed and refuses until a budget
  exists.
- **Localisation**: `localisation.locales` is `[]`. This project has no locale files. The
  localisation workflow is installed and refuses until a locale is listed.
